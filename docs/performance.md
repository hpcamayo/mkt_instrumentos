# Marketplace performance and reliability

Implemented September 2026, preserving the public pending-submission and admin-approval model.

## Browsing

- Catalog and store inventories show 24 listings per page. Pagination preserves repeated filter parameters. Sort orders include an ID tie-breaker.
- `listing_photo_count(listings)` is a stable, security-invoker Postgres computed field. Each listing query obtains its photo count without downloading all photo rows or a second HTTP request. Photo RLS still applies.
- Listing detail renders its product information first. Similar listings, seller recommendations, and inventory counts stream through Suspense. React request caching shares the seller query between its two consumers.
- Product photos, thumbnails, store assets, and the homepage background use Next Image with responsive sizes. Approved storage hosts are configured in `next.config.ts`; originals remain available in Storage. Thumbnails load lazily.
- Homepage sections render on the server, without animation-only client code or initially invisible content. Existing hover styles remain.
- Public pages still read fresh marketplace data on each request so moderation changes are immediately reflected. No shared authenticated-content cache was added.

## Authentication and publication

- Middleware runs only on account/admin surfaces and uses validated claims. Public SSR browsing does not revalidate user sessions. Protected page handlers continue their own checks; admin APIs retain authorization. Sprint 4 telemetry POSTs resolve a trusted actor separately; public live private-photo references stream without an Auth lookup, while nonpublic photo requests validate owner/admin access.
- Duplicate-email checks use a service-role-only `auth_email_exists(text)` lookup against the normalized Auth email and its existing index. They no longer download the user directory. Database failures produce an error, never an availability claim.
- A database trigger sets `published_at` on first approval and preserves it when reapproved. Existing approved rows without a date use their creation timestamp because their historical approval time is unknown.

## Submission recovery

- Images upload directly from the browser to Storage, avoiding server request-size limits.
- `/api/submissions` issues a signed capability for a random submission ID. Particular listing capabilities are bound to the authenticated user and upload under that user's storage folder. The server validates all fields and verifies uploaded paths before finalizing. Neither service-role credentials nor arbitrary object-deletion access is exposed to the browser.
- `complete_public_submission` atomically inserts an owned pending Particular listing, an owner-bound store application, or owner-bound store inventory. Listing submissions retain the 2–10 photo rule. It is callable only by the service role, and repeated finalization with the same ID does not overwrite or duplicate records.
- Upload failures attempt to remove partial uploads. If cleanup fails, the retry token is retained so another attempt can reuse/clean the folder.
- If the final response is lost, retry uses the same token without uploading again. Keep the form open and retry with the same values/files. Tokens are held in form memory; closing the page discards the attempt. Browser abandonment can still leave unreferenced storage objects; automatic orphan retention/cleanup is not configured.
- Legacy anonymous listing rows remain compatible, while new Particular, store-application, and store-inventory capabilities are bound to their authenticated account and owner-folder paths.

## Store concurrency and visibility

- Store inventory has a database-enforced 50-row concurrent cap across `pending` and `approved`. A per-store transaction advisory lock serializes capacity-consuming inserts/restores, so simultaneous requests at 49 cannot produce 51.
- Store listings are publicly readable only when both the listing is approved and the parent store is active. Photo RLS follows the same predicate.
- Store verification locks the store, validates every pending listing, flips trust state, and approves the pending set in one transaction. Any malformed pending row aborts the whole operation.
- Verification revocation removes future direct-publication authority without changing already-approved inventory.

## Listing lifecycle and revision reliability

- Owner edit, hide/restore, sold, relist, listing review, and revision review operations lock the target row and execute as single Postgres transactions. Direct client status/authority writes remain blocked.
- Approved Particular/normal-Tienda moderated edits are isolated in one pending revision; the live row and photos stay readable until approval. The pending unique index prevents competing proposals. The listing row lock serializes proposal amendment, merges the latest field/photo state, increments a revision version, and cancels an empty proposal.
- Admin revision decisions compare the submitted expected version with the locked latest row. A stale approval/rejection aborts instead of resolving an older proposal snapshot.
- Owner/admin hide state is orthogonal to revision review: approving a proposal never republishes a hidden listing. Store verification leaves existing proposals pending, while a later verified direct moderated edit atomically cancels any superseded proposal before applying the new live values.
- Sold rows are immutable history. Relisting inserts a new linked row with a new slug and reuses photo records without rewriting or deleting the source objects.
- Store restores and relists still pass through the existing serialized 50-item trigger. Concurrent attempts at the final slot cannot create a 51st pending/approved row.
- Listing edit uploads use fresh owner/listing/attempt-scoped paths in the private `listing-edit-photos` bucket. Browser storage policies permit append only, not overwriting/deleting history; new edit staging in the legacy public bucket is denied.
- The database accepts a proposed photo URL only when it is already in the listing's live/pending set or maps to an owned ≤5 MB JPEG/PNG/WebP private object at its exact edit path. A literal-dot extension check fixes normal PNG/JPEG/WebP additions; admin promotion validates pending references rather than uploader/admin identity. API and direct authenticated RPC calls retain the same 2–10, uniqueness, ownership, and media boundaries.
- Authenticated owner updates and live-photo row mutations are denied at the generic table-policy layer; lifecycle and edit changes enter through the validated, row-locked RPCs so direct clients cannot bypass taxonomy, revision, history, or photo-set invariants.
- Listing/store lifecycle notifications are created in the same moderation transaction. RLS-scoped indexes support newest-first and unread-count reads, while the mark-read RPC cannot mutate event ownership or targets.

## Sprint 4 photo recovery and privacy (production implementation)

- A signed HTTP edit capability binds the authenticated owner/listing to one attempt. The row-locked edit RPC stores a SHA-256 payload/result receipt: identical response-loss retries reuse the result without increasing revision version; changed input with the same attempt fails. Compatibility calls without an attempt ID still use the existing validated edit path.
- Private edit objects use durable `/api/listing-images/...` references. The server proxy permits approved live inventory and retained sold-history references only with an active parent store where applicable; owners/admins can inspect retained nonpublic live/revision evidence. Unreferenced uploads and unrelated requests return 404. Proxy responses are `private, no-store`; promotion changes database references in the approval transaction, not an asynchronous Storage-copy job.
- Reorder/add/remove/replace/revert operations submit the complete ordered effective set. Approving or rejecting an amended text/photo proposal remains atomic and version-aware; rejected/superseded/sold/relist references are retained. Reverting an empty proposal releases only its unused proposal photo component.
- Owner cleanup claims eligible paths under the same listing lock used for edits. A permanent `(bucket, path)` retirement marker prevents attachment after the reference check; cleanup excludes every live and historical revision reference across listings, including copied relist/sold references. A failed Storage deletion can retry the claim. The UI/server cleanup path does not grant arbitrary object deletion.
- Existing public initial-listing/store assets and already-public edit URLs are preserved, not retroactively made private. Known legacy public URLs remain retrievable independently of database moderation. No automatic abandoned-upload retention job is configured.

## Sprint 4 first-party events and grouped analytics (production implementation)

- Telemetry is mutation-only: the session, event, compatibility view, and contact routes record through POST. SSR, GET/HEAD, RSC prefetch, recommendations streaming, and image delivery do not record views or funnel transitions. Existing browsing queries/pagination/streaming remain unchanged.
- A listing-card impression requires at least 50% IntersectionObserver visibility while the document is visible. Detail/store view effects also require visible browsing. A canonical search signature ignores pagination; signed search receipts contain existing filters plus the actual SSR result count, preventing forged counts and a parallel search implementation.
- Event UUIDs protect response-loss retries. Listing impressions/views and store views additionally use a rolling 30-minute type/entity/identity window with a transaction advisory lock, preferring Auth identity over a signed random anonymous session. The 24-hour first-party session cookie is HttpOnly, SameSite=Lax, and Secure in production; it is not derived from IP, user agent, or a fingerprint. Owner/admin commercial inspections are excluded. Distinct real WhatsApp clicks are distinct contact actions, not automatically unique buyers.
- The browser queue is capped at 200 pending events, flushes at most 20 per request after 80 ms, and gives session/event transport an 8-second timeout. One lost-response retry reuses the same UUIDs. A bounded 500-entry browsing dedupe cache limits client memory. Failure drops best-effort telemetry without blocking browsing.
- Trusted event RPC transport has a 1.5-second timeout, so recording cannot indefinitely delay signed submission starts or contacts. WhatsApp navigation has a separate 900 ms deadline and always falls back to its real existing URL if telemetry/session transport fails; it never requires event success before contacting a seller. No message/draft text or auth secrets enter contact metadata.
- Raw event tables are RLS-enabled with no anonymous/authenticated table grants; the service-only recorder derives canonical seller/store attribution and public visibility. Actual moderation/application lifecycle triggers record inside the domain transaction, while creation/application starts are emitted by the trusted signed start path. The original 16-type taxonomy is extended by trusted favorite actions and production Sprint 6 confirmation/verified/review events; browser payloads still cannot forge them.
- Accepted deduplicated detail views increment the existing `view_count` exactly once. Historical cached values remain intact, with no fabricated backfill; all-history view displays include them, whereas 7/30-day windows and CTR/contact-rate denominators use only recorded events. Current active/sold counts are labeled current inventory state; approved inventory beneath a nonactive store is not counted active. Zero denominators produce «Sin datos», and contacts/sold labels do not imply verified sales or revenue.
- Indexed, grouped `get_account_analytics`/`get_marketplace_admin_analytics` RPCs replace placeholder metrics without per-listing count requests or downloading the raw log. Owner context comes from `auth.uid()`; foreign/global reports require admin authority. Recent/listing/store/seller/identity indexes and the partial authenticated-contact index support current aggregation and later eligibility. React request caching shares a private aggregate within the request, never across accounts.

## Sprint 6 transaction/review reliability (production implementation)

- Candidate lookup uses one indexed listing/actor/time aggregate over exact-listing authenticated WhatsApp events. It returns no email, phone or raw payload and never performs a user-directory search. The listing-first partial index avoids a global event scan.
- Listing-row and claim-row locks plus partial/ordinary unique indexes serialize competing selections, confirmation/cancellation, identical retries and exactly-one verified relation. A decline is retained and is rejected by both the candidate query and claim RPC; external attribution never creates review eligibility.
- Review submission locks the verified relationship and relies on `(transaction_id, direction)` uniqueness. Database `clock_timestamp()` owns the submission boundary; visibility is derived from paired rows or database deadline, so no scheduler is required. Public/store/Particular/buyer aggregate helpers use grouped queries and exclude unrevealed/admin-hidden content.
- Relist copies receive a new listing identity and therefore cannot inherit claims, transactions or reviews. All transaction/review foreign keys use restrictive deletion and preserve the sold historical anchor.
- Transaction/review/report tables are RLS-enabled and have no browser table grants. Guarded RPCs derive participant/admin authority from Auth. Anonymous calls reach explicit `42501` guards rather than a known local PostgREST/Postgres 17 revoked-default-function crash path; trusted implementations and visibility helpers live in the revoked `laria_private` schema.
- `/api/contact` and `/api/events` return a correlation ID. Event-write failures log only request ID, type and bounded category/code—never profile/contact/token payloads—and cannot block the real WhatsApp destination.
- The admin transaction view is a single bounded joined query (latest 100 claims), not one request per card. Listing/store pages perform one reputation aggregate each; account transaction center/detail RPCs return grouped participant-specific JSON.

The bounded release window had no error-level, 5xx/503, marketplace-event failure or sensitive-fixture log entries; observed event endpoint traffic was 200. All disposable records were removed. This was not a load benchmark and did not alter the existing September performance/reliability invariants.

## Sprint 7 email/search-alert reliability (local implementation)

- Publication matching is prospective. The migration inserts only first-public markers for the existing catalog, never historical matches or deliveries. New publication checks use an indexed category/type bucket before exact canonical filters; it does not scan every listing against every alert or backfill old inventory.
- `(alert_id, listing_id)`, semantic active-alert identity and outbox `dedupe_key` uniqueness own logical idempotency. Immediate keys use alert/listing; daily keys use alert/Lima date; price-drop keys reuse the authoritative transition/recipient. `FOR UPDATE SKIP LOCKED` claims and alert row locks prevent concurrent workers or pause/delete races from creating a second logical send.
- Domain transitions append an outbox row in Postgres and never wait for Resend. The worker sends at most four 25-row claims per invocation and at most five provider requests concurrently. Retryable failures back off 5 minutes, 30 minutes, 2 hours and 8 hours; attempt count is capped at five. A 15-minute stale processing lock is recovered without changing the delivery identity.
- Daily windows use `America/Lima`, only completed dates after 08:00, up to 100 alert digests per date, with a bounded seven-day catch-up replay. Zero-match dates create no job. A worker replay or concurrent prepare sees the same dedupe rows and is safe.
- Pausing/deleting cancels pending, retrying or claimed alert jobs and suppresses unsent daily matches. Resume advances `active_since`; pause-period inventory is never reconsidered. Soft deletion preserves delivery evidence, while complete account deletion cascades private fixtures safely.
- Outbox/match tables are in a schema revoked from browser roles. The worker requires a constant-time `CRON_SECRET` bearer check; service RPCs recheck `auth.role()`. Logs contain only correlation/delivery IDs and bounded failure codes, never bodies, tokens or recipient addresses. No tracking pixel/open metric is implemented.
- PRE-GO-LIVE Vercel Hobby has no automatic worker registration; controlled QA invokes the protected route manually. This deliberately has no Immediate-email latency SLA. A supported 5–15 minute automatic cadence plus retry/digest smoke is mandatory before marketplace go-live.
- Clean reset, all ten rollback-only SQL suites, every prior integration, the new alert API/RLS/queue integration, mocked provider/worker tests, 140 unit tests, lint, typecheck and build are the local release gate. This is functional/race verification, not a production load or deliverability benchmark.

## Checks

Sprint 5 reliability additions (deployed 2026-09-18): favorite states are registered once in a shared context, batched after 25 ms with at most 100 IDs per request, and never fetched separately per card. Unknown/failed state is unavailable rather than false; successful mutations update the shared state. Header controls use one trusted private hydrated state path, without a public SSR Auth query or importing the browser Auth SDK into the global provider. Listing IDs accept historical Postgres UUIDs rather than misusing the stricter event-ID validator.

The listing row lock serializes favorite mutations with live price changes; unique relations and transition/recipient constraints make repeated requests idempotent. Atomic fan-out uses indexed favorite lookups, and aggregate RPCs use grouped current-count/event queries rather than downloading identities. This matches the upstream [supautils permission-hint bug](https://github.com/supabase/supautils/issues/214). Hosted `supautils.hint_roles` remained `anon, authenticated, service_role`; no production workaround was needed or applied. Upgrade the local Postgres image to a fixed release when available; the diagnostic hint setting can then be restored with `ALTER SYSTEM RESET supautils.hint_roles` and `pg_reload_conf()`. This runtime workaround is not part of the product schema or a production release step. Reproduction commands are in `docs/sprint-4-verification.md`.
