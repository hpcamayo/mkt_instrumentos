## Remediation (local, uncommitted — 2026-09-27)

1. **`/admin/tiendas` 500 — fixed.** `DomainCard` passed an undeclared `status` to `AdminStoreEditor`/`AdminListingEditor`. TypeScript accepted it because the DOM lib types the deprecated global `window.status`; in the browser it silently evaluated to `""`, and during server rendering Node has no such global, so any Admin `tiendas`/`publicaciones` page with at least one record threw `ReferenceError: status is not defined`. The card now uses the record's own `status`. Pre-existing since Sprint 8 (`0bda8e0`), not introduced by Sprint 9. Guards: `no-restricted-globals` ESLint rule for bare browser globals in `app/`, `components/`, `components_v0/`, `lib/`, which flags the pre-fix file; `tests/sprint-9-gate.test.cjs` server-renders both domains and reproduces the original ReferenceError with the pre-fix source.
2. **Homepage `og:url` — fixed.** `buildHomeMetadata()` in `lib/seo.ts` sets the homepage canonical and `og:url` to the absolute site root; the root layout still sets no site-wide URL. Next.js serializes the root URL as `https://laria.audio` (no trailing slash: it renders a root pathname as the origin), which is the same URL as `https://laria.audio/`. Rendered locally: every representative public page emits `og:url` equal to its canonical.
3. **`/registro/vendedor` 504 — mechanism reproduced, no Sprint 9 cause.** The page is statically prerendered; its only per-request code is `middleware.ts`, which matches `/registro/:path*` (as well as `/login`, `/logout`, `/vender`, `/mi-cuenta`, `/admin`) and awaits `supabase.auth.getClaims()` without a timeout. With no Supabase session cookie this needs no network. With a session cookie, auth-js calls Supabase Auth (`getUser` for symmetric JWTs, JWKS otherwise). Local production build + stub Auth: anonymous and healthy-Auth requests to `/registro/vendedor`, `/registro/tienda` and `/login` return in <60 ms; with an unresponsive Auth endpoint, all three stall until the client timeout, while `/terminos` (outside the matcher) stays at ~5 ms. `middleware.ts`, `lib/auth` and `lib/supabase` are unchanged from `bb16e31`; Sprint 9's noindex metadata is static and `X-Robots-Tag` is a static routing header, so neither adds request work. The production 504 is therefore most consistent with a slow/unavailable Supabase Auth response to a cookie-bearing request, not deterministic application behavior; `/registro/tienda` and every other matched route share the same exposure. No code change was made. Bounding the middleware auth call is a possible hardening, but it would change authentication behavior and needs its own decision.

## Googlebot `/listados` metadata investigation (local, 2026-09-27)

Method: production builds against the local read-only REST fixture, raw HTML fetched with the Googlebot user agent, and the rendered DOM checked in headless Chromium (Playwright) after hydration. Each variant was built from a clean copy and served by a freshly started server.

- **Symptom:** for Googlebot and ordinary browsers, `/listados` emits `<title>`, canonical, `og:url` and the other metadata inside `<body>`. Chromium confirms they stay in `<body>` after hydration; React does not move them to `<head>`. Bingbot and other HTML-limited bots receive them in `<head>`. All other public routes put them in `<head>` for every crawler.
- **Root cause:** `app/listados/loading.tsx` is the only route-level Suspense boundary in the app. Next.js 15.5 serves metadata as a streamed, non-blocking boundary to non-HTML-limited user agents, and Googlebot is hard-coded as such a bot. The loading fallback lets the shell and `<head>` flush before metadata resolves, so the metadata is written into the body. Pages without a loading boundary finish their data before the shell flushes, so their metadata is hoisted into `<head>`.
- **Not a Sprint 9 regression:** the pre-Sprint 9 shape (static metadata plus `loading.tsx`) reproduces the same body placement. Sprint 9 only added a canonical and `og:url` to what was already streamed.
- **Verified fixes:** both pass the full smoke, including the Chromium Googlebot rendered check, with 24 listings still in the Googlebot HTML.
  - **A. Remove `app/listados/loading.tsx`.** Metadata goes into `<head>` for every user agent, but visitors lose the catalog loading skeleton and the first byte waits for the catalog query.
  - **B. Add Googlebot to `htmlLimitedBots` in `next.config.ts`,** keeping Next's default list. Googlebot gets metadata in `<head>` while the page still streams; visitors keep the skeleton. The cost is keeping the copied default list in step with future Next.js releases.
- **Decision: option B implemented (local, uncommitted).** `next.config.ts` sets `htmlLimitedBots` to `Googlebot` plus Next's own `HTML_LIMITED_BOT_UA_RE`, imported rather than copied so its default bots follow Next.js upgrades. If that internal module moves, the build fails. On a local production build, Googlebot gets `/listados` metadata in the initial `<head>` with all 24 listings, visitors keep the skeleton, and the full SEO smoke passes for both crawlers without a browser. `tests/sprint-9-gate.test.cjs` checks the setting through Next's own streaming-metadata decision function.
